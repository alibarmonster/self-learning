## Q1. HTTP / Internet -> Cloud Run / Cloud Run functions / App Engine (public vs authenticated, ingress, Domain Restricted Sharing)

### Takeaway
A Cloud Run service is private by default; an internet edge is valid only if the service either has the invoker IAM check disabled (now the recommended way to go public) or grants `allUsers` `roles/run.invoker`, AND its ingress is `all` (or `internal-and-cloud-load-balancing` when the edge comes through an external Application Load Balancer). The two classic failures are a 403 from IAM ("Your client does not have permission to get URL") and a 404 from ingress; an org with Domain Restricted Sharing rejects the `allUsers` binding with "One or more users named in the policy do not belong to a permitted customer."

### Cited Findings
- Verbatim 403 when a browser hits a private service: "HTTP 403: Forbidden: Your client does not have permission to get URL from this server." Cause: browsers don't send an ID token. Fix: use IAP, `gcloud run services proxy` for testing, or allow public access. — [Cloud Run troubleshooting](https://docs.cloud.google.com/run/docs/troubleshooting)
- Verbatim 403 variant: "HTTP 403: The request was not authenticated. Either allow public access or set the proper Authorization header". Fix: grant the caller `run.routes.invoke` (normally via `roles/run.invoker`). — [Cloud Run troubleshooting](https://docs.cloud.google.com/run/docs/troubleshooting)
- Verbatim 401: "HTTP 401: The request was not authorized to invoke this service". Fix: the token's audience must match the service URL or custom audience; send an ID token (not an access/refresh token) in a single `Authorization: Bearer` header. — [Cloud Run troubleshooting](https://docs.cloud.google.com/run/docs/troubleshooting)
- Verbatim 404 from ingress: "HTTP 404: Not found". Cause: request blocked before reaching the container, often by an Internal ingress setting or a disabled `run.app` URL; these 404s may not appear in request logs. — [Cloud Run troubleshooting](https://docs.cloud.google.com/run/docs/troubleshooting)
- Two ways to go public: (1) disable the Invoker IAM check (marked recommended): `gcloud run deploy SERVICE --no-invoker-iam-check` / `gcloud run services update SERVICE --no-invoker-iam-check`, annotation `run.googleapis.com/invoker-iam-disabled: 'true'`, Terraform `invoker_iam_disabled = true`; (2) grant `allUsers` `roles/run.invoker` (`gcloud run services add-iam-policy-binding SERVICE --member="allUsers" --role="roles/run.invoker"`, or `--allow-unauthenticated` at deploy). Re-enabling the check in the console removes existing `allUsers` invoker bindings. — [Allow public access (Cloud Run)](https://docs.cloud.google.com/run/docs/authenticating/public)
- The `allUsers` instructions "won't succeed if your project is under a domain restricted sharing organization policy"; in that case disable the Invoker IAM check instead. Admins can restrict disabling it with managed constraint `constraints/run.managed.requireInvokerIam` (not enforced by default). Permissions needed: `run.services.setIamPolicy` (plus `run.services.create`/`update` to toggle the check); all in `roles/run.admin`. — [Allow public access (Cloud Run)](https://docs.cloud.google.com/run/docs/authenticating/public)
- Domain Restricted Sharing constraint is `iam.allowedPolicyMemberDomains` (legacy list constraint) with a newer managed constraint `iam.managed.allowedPolicyMembers`; for organizations created on or after May 3, 2024 it is "enforced by default" with your domain as the only allowed value. The gcloud error when a blocked principal is added: "One or more users named in the policy do not belong to a permitted customer." With DRS, "users outside of your organization won't be able to access public Cloud Run services"; workaround: disable the Invoker IAM check (or tag-conditioned custom policy exceptions for `allUsers`/`allAuthenticatedUsers`). — [Restricting identities by domain](https://docs.cloud.google.com/resource-manager/docs/organization-policy/restricting-domains)
- Same error string seen in the wild on IAM setPolicy calls — [Fivetran troubleshooting](https://fivetran.com/docs/destinations/bigquery/troubleshooting/domain-restricted-identity-error); a community thread reports DRS blocks run.invoker for `allUsers` on Cloud Run — [Google Developer forum](https://discuss.google.dev/t/unable-to-grant-run-invoker-permission-to-the-allusers-identity-cloud-run-drs-enabled/170807)
- Ingress settings: `all` allows "all requests, including requests directly from the internet to the `run.app` URL"; `internal-and-cloud-load-balancing` allows internal sources plus the external Application LB, and "Direct requests to the `run.app` URL from the internet are not allowed"; `internal` allows internal ALBs, VPC networks in the same project (and Shared VPC), VPC-SC perimeter resources, and listed Google services. Org policy `run.allowedIngress` can restrict which values developers choose. — [Cloud Run ingress](https://docs.cloud.google.com/run/docs/securing/ingress)
- IAP can now be enabled directly on Cloud Run (no load balancer) via the `--iap` flag; users need `roles/iap.httpsResourceAccessor`; the IAP service agent `service-PROJECT_NUMBER@gcp-sa-iap.iam.gserviceaccount.com` needs `roles/run.invoker` on the service. "You cannot configure IAP on both the load balancer and the Cloud Run service." "Cloud Run enforces IAP policies before performing IAM checks on the IAP service account", so services like Pub/Sub that rely on their own authentication might fail. Error headings listed: "Out-of-org user access: Disabled", "Brand is currently set to internal", "Setting IAM permissions failed". — [IAP for Cloud Run](https://docs.cloud.google.com/run/docs/securing/identity-aware-proxy-cloud-run)
- App Engine: "By default, your App Engine app accepts traffic from all network origins"; an App Engine firewall can allow or deny requests; VPC Service Controls is "Not supported" in the App Engine standard environment. — [App Engine application security](https://docs.cloud.google.com/appengine/docs/standard/application-security)
- External Application Load Balancers don't support end-user authentication to Cloud Run; IAP is suggested for users inside your organization. — [Serverless NEG concepts](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts)

### Inferences
- Simulator rule set for `Internet -> Cloud Run`: valid iff (`invokerIamCheck == disabled` OR `allUsers` has `run.invoker`) AND `ingress == all` AND `run.app URL not disabled`. Otherwise: no public principal -> 403 "Your client does not have permission to get URL from this server."; ingress `internal` or `internal-and-cloud-load-balancing` -> 404 "Not found"; DRS enforced + learner tries `allUsers` -> deploy-time policy error "One or more users named in the policy do not belong to a permitted customer."
- For `Internet -> Cloud Run functions` the same Cloud Run rules apply (functions are Cloud Run services), see Q10.
- For `Internet -> App Engine`, the main simulated failure is the App Engine firewall/ingress setting rather than IAM; App Engine apps are public by default.

### Gaps
- No verbatim text found for App Engine firewall denials or App Engine ingress values (`all`, `internal-only`, `internal-and-cloud-load-balancing`); the application-security page only links to "Specify ingress settings".
- Console (not gcloud) wording of the DRS error is only shown as a screenshot in Google's docs.

## Q2. Load balancer -> serverless NEG -> Cloud Run; LB -> MIG (health check firewall); LB -> backend bucket; Cloud CDN, Cloud Armor, IAP

### Takeaway
A serverless NEG is valid only behind an Application Load Balancer (never a Network LB), points to exactly one Cloud Run / Cloud Run functions / App Engine / API Gateway resource in the same region as the NEG, and has no health checks. MIG backends need an ingress firewall rule from the Google health-check range or they are marked unhealthy (502 on classic ALB, 503 on others). Backend buckets work only on global external / classic ALBs and not with IAP; IAP and Cloud CDN cannot share a backend service.

### Cited Findings
- "Serverless NEGs are not supported by proxy Network Load Balancers and passthrough Network Load Balancers." Supported: global external and classic Application LBs, plus regional external, regional internal and cross-region internal Application LBs (with restrictions). — [Serverless NEG concepts](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts)
- Supported serverless NEG backends: Cloud Run (including Cloud Run functions), Cloud Run functions (1st gen), App Engine standard and flexible, API Gateway (Preview). — [Serverless NEG concepts](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts)
- Region: a NEG can only point to a resource "residing in the same region as the NEG"; "A serverless NEG can't have more than one endpoint"; global backend services can hold several serverless NEGs but only one per region; regional backend services only one. Multi-region needs Premium tier and is not supported with App Engine. — [Serverless NEG concepts](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts)
- "Health checks are not supported for serverless backends." You "can't specify a balancing mode"; session affinity "won't work"; serverless NEGs can't share a backend service with other NEG types; Cloud Run NEGs only combine with Cloud Run NEGs, App Engine only with App Engine; backend timeout is fixed (60 min); regional LBs limited to 5000 QPS per project for serverless NEG traffic. — [Serverless NEG concepts](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts)
- "IAP and Cloud CDN are incompatible with each other. They can't be enabled on the same backend service." Cloud Armor protects serverless services through an external ALB with "some limitations... especially for Cloud Run and App Engine." — [Serverless NEG concepts](https://docs.cloud.google.com/load-balancing/docs/negs/serverless-neg-concepts)
- Ingress `internal-and-cloud-load-balancing` lets the service "Accept requests from the internet through the external Application Load Balancer" while blocking direct internet requests to `run.app`. — [Cloud Run ingress](https://docs.cloud.google.com/run/docs/securing/ingress)
- Health-check probe source ranges for ALBs with instance groups / zonal NEGs: IPv4 `35.191.0.0/16`, IPv6 `2600:2d00:1:b029::/64`. Google "requires that you create the necessary ingress `allow` firewall rules"; otherwise the implied deny rule blocks probes and "the load balancer considers your backends to be unhealthy." Classic ALB "Returns an HTTP `502` status code to clients when all backends are unhealthy"; global external, regional external and internal ALBs return HTTP 503. Serverless NEGs: "Not applicable (these backends don't support health checks)." Regional Envoy-based ALBs with hybrid NEGs probe from the proxy-only subnet. — [Health check concepts](https://docs.cloud.google.com/load-balancing/docs/health-check-concepts)
- Backend buckets: "Backend buckets are only supported with global external Application Load Balancers and classic Application Load Balancer"; not supported with IAP. Public site: grant `allUsers` `roles/storage.objectViewer`. Private bucket: grant the role to `service-PROJECT_NUM@https-lb.iam.gserviceaccount.com`, created automatically with the backend bucket (read-only access). Signed URLs need Cloud CDN enabled. Unsupported query parameters (e.g. `cors`, `lifecycle`) return HTTP 404 "Unsupported query parameter". — [Backend buckets](https://docs.cloud.google.com/load-balancing/docs/https/ext-load-balancer-backend-buckets)

### Inferences
- Simulator validation for `LB -> serverless NEG -> Cloud Run`: reject if LB type is a Network LB; reject if NEG region != service region; reject a health check attached to the serverless backend; warn if service ingress is `internal` (external LB traffic would 404) - use `internal-and-cloud-load-balancing`; IAM still applies, so a private service behind an external LB still returns 403 to browsers unless the invoker check is disabled/`allUsers` is granted or IAP is on.
- `LB -> MIG`: require a firewall ingress allow from `35.191.0.0/16` (and IPv6 range) on the health-check port; if missing, show backends UNHEALTHY and 502 (classic) / 503 (global external).
- Note for course content: many older study guides also list `130.211.0.0/22` as a health-check source; the current health-check concepts page fetched in this session lists only `35.191.0.0/16` (+ IPv6) for ALBs. Treat `130.211.0.0/22` as legacy/possibly still accepted but not in the current table.
- `LB -> backend bucket`: if the bucket is not public and the `https-lb` service agent lacks `storage.objectViewer`, requests would fail with a Cloud Storage access-denied response (exact text not found).

### Gaps
- Exact Cloud Armor limitations for serverless NEGs and backend buckets (e.g., edge policies only) were not enumerated on the fetched pages.
- No verbatim error text for a private backend bucket access denial through the LB.
- Static website index/404 page configuration on backend buckets not covered.

## Q3. Pub/Sub -> Cloud Run push, -> Cloud Run functions (Eventarc), -> BigQuery subscription, -> Cloud Storage subscription, -> Dataflow -> BigQuery

### Takeaway
Pub/Sub supports pull, push, BigQuery and Cloud Storage subscriptions. Push to a private Cloud Run service needs a push-auth service account with `roles/run.invoker` on that service (and, only for projects whose Pub/Sub service agent dates from on or before 2021-04-08, `roles/iam.serviceAccountTokenCreator` for the Pub/Sub service agent). BigQuery subscriptions need the Pub/Sub service agent (or a custom SA) to hold `roles/bigquery.dataEditor`; Cloud Storage subscriptions need `roles/storage.objectCreator` + `roles/storage.legacyBucketReader`. Dataflow needs a worker SA with `roles/dataflow.worker` plus source/sink roles.

### Cited Findings
- Push to Cloud Run: create invoker SA; grant `roles/run.invoker` on the Cloud Run service (not the project): `gcloud run services add-iam-policy-binding pubsub-tutorial --member=serviceAccount:cloud-run-pubsub-invoker@PROJECT_ID.iam.gserviceaccount.com --role=roles/run.invoker`; "It can take several minutes for the IAM changes to propagate." — [Pub/Sub push to Cloud Run](https://docs.cloud.google.com/run/docs/triggering/pubsub-push)
- Pub/Sub service agent `service-PROJECT_NUMBER@gcp-sa-pubsub.iam.gserviceaccount.com` needs `roles/iam.serviceAccountTokenCreator` on the project only "If your project was created on or before April 8, 2021"; later projects' agent already has `roles/pubsub.serviceAgent` with identical permissions. — [Pub/Sub push to Cloud Run](https://docs.cloud.google.com/run/docs/triggering/pubsub-push)
- Subscription: `gcloud pubsub subscriptions create myRunSubscription --topic myRunTopic --ack-deadline=600 --push-endpoint=SERVICE-URL/ --push-auth-service-account=cloud-run-pubsub-invoker@PROJECT_ID.iam.gserviceaccount.com`; deploy the service with `--no-allow-unauthenticated`; success codes (200/204) ack, error codes cause retry. — [Pub/Sub push to Cloud Run](https://docs.cloud.google.com/run/docs/triggering/pubsub-push)
- Push endpoints are "a publicly addressable server or a webhook"; ack codes 102, 200, 201, 202, 204; any other status is a nack and triggers push backoff of 100 ms to 60 s. — [Pub/Sub push subscriptions](https://docs.cloud.google.com/pubsub/docs/push)
- Pub/Sub subscriptions count as "internal" for Cloud Run ingress when in the same project or VPC-SC perimeter and using the default `run.app` URL (not a custom domain). — [Cloud Run ingress](https://docs.cloud.google.com/run/docs/securing/ingress)
- Third-party troubleshooting (2026): a platform-generated 403 on push usually means the push SA lacks `run.routes.invoke` (in `roles/run.invoker`) on that exact service/region; if the service is in another project, grant there; a 403 with no Cloud Run request log can indicate a VPC-SC block. — [OneUptime blog](https://oneuptime.com/blog/post/2026-08-27-fix-pubsub-push-403-cloud-run/view); [adhdecode](https://adhdecode.com/debugging/cloud-run/cloud-run-pubsub-push-subscription-auth-failed/)
- Pub/Sub -> Cloud Run / Cloud Run functions via Eventarc: event type `google.cloud.pubsub.topic.v1.messagePublished`; "Your Eventarc trigger's service account must have the permission to invoke your service"; "By default, Cloud Run uses the Compute Engine default service account"; topic and service in same project as trigger; trigger location "must match the location of the Google Cloud service that is generating events" and the destination "doesn't need to be in the same location as the trigger". Command: `gcloud eventarc triggers create TRIGGER --location=LOCATION --destination-run-service=FUNCTION --event-filters="type=google.cloud.pubsub.topic.v1.messagePublished" --transport-topic=projects/PROJECT_ID/topics/TOPIC_ID --service-account=SA@PROJECT_ID.iam.gserviceaccount.com`; functions deployed first with `gcloud run deploy FUNCTION --source . --function ENTRYPOINT`. — [Pub/Sub triggers (Cloud Run)](https://docs.cloud.google.com/run/docs/triggering/pubsub-triggers)
- Eventarc -> authenticated Cloud Run tutorial grants `roles/run.invoker` on the project to the trigger SA ("grants the role on all Cloud Run services and jobs in a project"); without it "the trigger will not work as expected" and logs show an authentication error; APIs: artifactregistry, cloudbuild, eventarc, pubsub, run. — [Eventarc Pub/Sub -> authenticated Cloud Run](https://docs.cloud.google.com/eventarc/standard/docs/run/pubsub-authenticated)
- BigQuery subscription: default principal is the Pub/Sub service agent, which needs `roles/bigquery.dataEditor` on the project or the specific table; with a custom SA, that SA needs Data Editor, the Pub/Sub service agent needs `iam.serviceAccounts.getAccessToken` on it, and the creator needs `iam.serviceAccounts.actAs` (e.g. `roles/iam.serviceAccountUser`). Creator needs `pubsub.subscriptions.create` + `pubsub.topics.attachSubscription` (in `roles/pubsub.editor`). — [Create BigQuery subscription](https://docs.cloud.google.com/pubsub/docs/create-bigquery-subscription)
- BigQuery subscription schema rules: without "Use topic schema"/"Use table schema" the table needs a `data` column of BYTES, STRING or JSON; only one schema option at a time; "Use table schema" needs JSON messages; missing fields must be NULLABLE; "Write metadata" adds `subscription_name`, `message_id`, `publish_time`, `data`, `attributes`; without "Drop unknown fields", messages with extra fields stay in the backlog unless a dead-letter topic is set; "BigQuery rejects messages that don't contain valid JSON." — [Create BigQuery subscription](https://docs.cloud.google.com/pubsub/docs/create-bigquery-subscription)
- "Any message that contains an improperly formatted field is not written to BigQuery"; failed writes are nacked and resent, then dead-lettered if configured; the dead-letter attribute `CloudPubSubDeadLetterSourceDeliveryErrorMessage` holds the reason. CDC requires `use_table_schema=true`, `_CHANGE_TYPE` (UPSERT/DELETE) and a primary key. — [BigQuery subscriptions](https://docs.cloud.google.com/pubsub/docs/bigquery)
- Cloud Storage subscription: Pub/Sub service agent needs `roles/storage.objectCreator` and `roles/storage.legacyBucketReader` (project or bucket); same custom-SA pattern as BigQuery; "A Cloud Storage bucket must already exist"; Requester Pays must be disabled; bucket can be in another project; console warning text: "Unable to verify if the Pub/Sub service agent has write permissions on this bucket." Formats: text or Avro (no Parquet). Batching: max duration 1-10 min (default 5). — [Create Cloud Storage subscription](https://docs.cloud.google.com/pubsub/docs/create-cloudstorage-subscription)
- Dataflow: service agent `service-PROJECT_NUMBER@dataflow-service-producer-prod.iam.gserviceaccount.com` with `roles/dataflow.serviceAgent`; worker SA defaults to `PROJECT_NUMBER-compute@developer.gserviceaccount.com` (user-managed recommended) and needs `roles/dataflow.worker`; Pub/Sub source needs `roles/pubsub.subscriber`; BigQuery sink `roles/bigquery.dataEditor` (reads `roles/bigquery.dataViewer`); staging/temp bucket read+write; submitter needs `iam.serviceAccounts.actAs` (`roles/iam.serviceAccountUser`) and may need `roles/dataflow.developer`; with `--usePublicIps=false` "Enable Private Google Access on your VPC subnet". — [Dataflow security and permissions](https://docs.cloud.google.com/dataflow/docs/concepts/security-and-permissions)

### Inferences
- Simulator rule for `Pub/Sub -> Cloud Run (push)`: require push-auth SA; require that SA to have `run.invoker` on the target service (project-level grant also satisfies it); if project is "legacy (<= 2021-04-08)" require token creator for the Pub/Sub agent; failure shows as push 403s and growing `subscription/push_request_count` with non-2xx `response_code` (metric name from Eventarc troubleshooting, Q4).
- Push to a private-IP-only endpoint (e.g. VM internal IP, Memorystore) is invalid because push needs a publicly addressable HTTPS endpoint; Cloud Run with `internal` ingress is still valid from same-project Pub/Sub.
- A simplified BigQuery-subscription validator: table exists AND (has `data` column OR schema option chosen) AND service agent has `bigquery.dataEditor`. Missing role -> messages accumulate / subscription error (exact text not found).
- Pub/Sub has no subscription type for Cloud SQL, Firestore, Spanner or Memorystore; those require a compute hop (Cloud Run/function/Dataflow).

### Gaps
- Verbatim Pub/Sub push 403 delivery error text (as shown in subscription metrics/logs) not found on official pages.
- Verbatim error for a BigQuery subscription whose service agent lacks `bigquery.dataEditor` not found (page says only "a compatibility-related error message" for schema issues).
- Dataflow firewall requirement between workers (commonly TCP 12345-12346) was not on the fetched page.
- Whether `roles/bigquery.metadataViewer` is still needed for BigQuery subscriptions: current page lists only `roles/bigquery.dataEditor`.

## Q4. Cloud Storage -> Cloud Run / Cloud Run functions via Eventarc; Cloud Storage Pub/Sub notifications

### Takeaway
Cloud Storage events reach Cloud Run through Eventarc (direct Cloud Storage events) or through bucket Pub/Sub notifications. Both require the Cloud Storage service agent (`service-PROJECT_NUMBER@gs-project-accounts.iam.gserviceaccount.com`) to have `roles/pubsub.publisher`; Eventarc additionally needs the trigger SA to hold `roles/eventarc.eventReceiver` (and `roles/run.invoker` for private targets), and the bucket must be in the same project and same region/multi-region as the trigger.

### Cited Findings
- APIs: `eventarc.googleapis.com pubsub.googleapis.com run.googleapis.com storage.googleapis.com`. Trigger SA (quickstart uses Compute Engine default SA) gets `roles/eventarc.eventReceiver` at project level. Cloud Storage service agent (from `gcloud storage service-agent --project=PROJECT_ID`) needs `roles/pubsub.publisher` on the project. Pub/Sub service agent needs token creator only if enabled on or before April 8, 2021. — [Eventarc Cloud Storage trigger (gcloud)](https://docs.cloud.google.com/eventarc/docs/run/create-trigger-storage-gcloud)
- Location: the bucket "must reside in the same Google Cloud project and" region or multi-region as the trigger. Event type in quickstart: `google.cloud.storage.object.v1.finalized` (also deletion, archiving, metadata updates). Trigger can take "up to two minutes"; first trigger may hit Eventarc service-agent provisioning delay. Projects with DRS should use an authenticated target. `iam.automaticIamGrantsForDefaultServiceAccounts` may stop Editor being auto-granted to default SAs. — [Eventarc Cloud Storage trigger (gcloud)](https://docs.cloud.google.com/eventarc/docs/run/create-trigger-storage-gcloud)
- Eventarc verbatim errors: "Permission denied while using the Eventarc Service Agent" (wait up to ~7 min; ensure `service-PROJECT_NUMBER@gcp-sa-eventarc.iam.gserviceaccount.com` has `roles/eventarc.serviceAgent`); "Failed to load service details: permission denied" (check trigger permissions and Pub/Sub SA token creator); cross-project: errors mentioning `iam.serviceAccounts.getAccessToken`, `iam.serviceAccounts.actAs`, "...cross-project service accounts are disabled," or "Failed to impersonate..."; trigger conditions `NOT_FOUND` "Pub/Sub topic not found. Try recreating the trigger." and `UNKNOWN` "Pub/Sub topic status is unknown. Try requesting the trigger description again." Diagnose undelivered events via `topic/send_message_operation_count` and `subscription/push_request_count` by `response_code`. — [Eventarc troubleshooting](https://docs.cloud.google.com/eventarc/docs/troubleshooting)
- Bucket Pub/Sub notifications: service agent `service-PROJECT_NUMBER@gs-project-accounts.iam.gserviceaccount.com` "must have the Pub/Sub Publisher role (`roles/pubsub.publisher`) on the Pub/Sub topic"; propagation delay of seconds (wait ~30 s if scripted); gcloud creates the topic if missing; requires Pub/Sub API in receiving project, Storage Admin on bucket and Pub/Sub Admin on project; cross-project topic uses full path `projects/PROJECT_B_ID/topics/TOPIC_NAME` with the bucket project's agent granted on it. — [Pub/Sub notifications for Cloud Storage](https://docs.cloud.google.com/storage/docs/reporting-changes)

### Inferences
- Simulator rule for `Cloud Storage -> Cloud Run (Eventarc)`: require bucket.region == trigger.location and same project; GCS agent has `pubsub.publisher`; trigger SA has `eventarc.eventReceiver`; if target private, trigger SA has `run.invoker`. Region mismatch should fail at trigger creation (exact error text not found).
- `Cloud Storage -> Cloud SQL` / `-> BigQuery` directly: Cloud Storage itself only emits notifications/events; loading into BigQuery or Cloud SQL is done by the destination service (BigQuery load job, Cloud SQL import) or by a compute hop - see INVALID list (Q11).

### Gaps
- Exact error string when an Eventarc Cloud Storage trigger's location does not match the bucket's location was not found.
- Full event-type list for Pub/Sub notifications (OBJECT_FINALIZE, etc.) was only linked, not shown, on the fetched page.
- Whether `gcloud storage buckets notifications create` auto-grants `pubsub.publisher` was not confirmed by the doc.

## Q5. Cloud Scheduler -> Cloud Run / Pub/Sub / App Engine; Cloud Tasks -> Cloud Run; Workflows -> services

### Takeaway
Scheduler, Tasks and Workflows all call Cloud Run with an OIDC ID token minted from a user-chosen service account in the same project; that SA needs `roles/run.invoker` on the target, and the human creating the job/task/workflow needs `roles/iam.serviceAccountUser` (actAs) on the SA. Use OAuth tokens only for `*.googleapis.com` targets. All three count as "internal" for Cloud Run ingress if same project and using `run.app`.

### Cited Findings
- Scheduler token type: "OIDC is generally used _except_ for Google APIs hosted on `*.googleapis.com` as these APIs expect an OAuth token" (`--oauth-service-account-email` selects OAuth). "The service account must belong to the project in which the Cloud Scheduler job is created." "Don't use the Cloud Scheduler service agent" as the token identity. Target role: `roles/run.invoker` for Cloud Run / Cloud Run functions; Cloud Functions Invoker for 1st gen. Job creator needs `roles/iam.serviceAccountUser` ("contains the `iam.serviceAccounts.actAs` permission"). — [Scheduler HTTP target auth](https://docs.cloud.google.com/scheduler/docs/http-target-auth)
- Scheduler service agent `service-PROJECT_NUMBER@gcp-sa-cloudscheduler.iam.gserviceaccount.com` needs `roles/cloudscheduler.serviceAgent`: "Without this role, Cloud Scheduler jobs fail"; auto-set when API enabled (manual only if enabled before March 19, 2019); revoking it "results in `403` responses to endpoints requiring authentication." Audience: optional; typically the target URL without parameters; if unset the entire URL including parameters is used. — [Scheduler HTTP target auth](https://docs.cloud.google.com/scheduler/docs/http-target-auth)
- Cloud Tasks: ID token for Google Cloud handlers such as Cloud Run, access token for `*.googleapis.com`; queue-level auth "overrides any authentication configured at the task level"; SA must "be in the same project as your Cloud Tasks queues"; "Cloud Tasks Enqueuer" role to add tasks; handler role "Cloud Run Invoker"; the Cloud Tasks service agent `service-PROJECT_NUMBER@gcp-sa-cloudtasks.iam.gserviceaccount.com` (role `roles/cloudtasks.serviceAgent`) is granted Service Account User on the target SA in the example. — [Cloud Tasks HTTP target tasks](https://docs.cloud.google.com/tasks/docs/creating-http-target-tasks)
- Workflows: requests carry no identity by default ("You must explicitly add authentication information to your workflow definition"); use OIDC for Cloud Run/functions (HTTPS only); the workflow's SA needs `roles/run.invoker` (also for Cloud Run functions, rather than Cloud Functions Invoker); Workflows can invoke internal-ingress services "in the same Google Cloud project" on the `run.app` URL, not a custom domain; Cloud Run jobs "do not listen for or serve HTTP requests" so use the Cloud Run Admin API connector. — [Workflows calling Cloud Run](https://docs.cloud.google.com/workflows/docs/calling-run-functions)

## Q6. Cloud Run / Cloud Run functions / App Engine / GKE / Compute Engine -> Cloud SQL

### Takeaway
Two independent checks: IAM (`roles/cloudsql.client` = `cloudsql.instances.connect` + `cloudsql.instances.get`, and the Cloud SQL Admin API enabled) for connector/Auth Proxy paths, and network (public IP via built-in Unix socket / connector, or private IP that needs the caller inside the instance's VPC: Direct VPC egress or a Serverless VPC Access connector for serverless, VPC-native cluster in same VPC for GKE). Direct public-IP TCP connections (no proxy) require authorized networks. As of 2026, Private Service Connect is the console default private-IP option for new projects.

### Cited Findings
- Cloud Run -> Cloud SQL: "Enable the Cloud SQL Admin API in the Google Cloud project that you are connecting from" (both projects if cross-project); runtime SA needs "Cloud SQL Client" (grant in the instance's project for cross-project). Public IP: Unix socket at `/cloudsql/INSTANCE_CONNECTION_NAME` (`project:region:instance-id`), auto-encrypted, socket path max 108 chars. Private IP: "Direct VPC egress and connectors use private IP addresses to handle communication to your VPC network"; instance must have private IP, connect to port 3306; same VPC (Cloud VPN and VPC Network Peering supported paths); "Direct VPC egress and Serverless VPC Access don't support legacy networks"; connector "must share the same project and region as the resource that uses it" (except Shared VPC). Same region recommended. "Cloud Run container instances are limited to 100 connections to a Cloud SQL database." — [Connect from Cloud Run](https://docs.cloud.google.com/sql/docs/mysql/connect-run)
- Connection options: direct public IP "must configure authorized networks"; connector (Auth Proxy / language connectors) on public IP avoids authorized networks; private IP via private services access (single VPC, VPC peering) or Private Service Connect (multiple VPCs/projects/orgs); "Private Service Connect is the default private IP connectivity option for new projects"; Cloud Run and App Engine "use an embedded Cloud SQL Auth Proxy". — [Cloud SQL connect overview](https://docs.cloud.google.com/sql/docs/mysql/connect-overview)
- "Private Service Connect is the default private IP connectivity option in the Google Cloud console for new projects" and is recommended over PSA; PSA is "an earlier type of private IP connectivity, based on VPC Network Peering" and "only allows connections from one VPC network". — [Cloud SQL private IP](https://docs.cloud.google.com/sql/docs/mysql/private-ip)
- Auth Proxy: Cloud SQL Client role; `cloudsql.instances.connect`; Admin API required - without it you may see "Error 403: Access Not Configured"; a `403 notAuthorized` error is associated with a SA lacking permission or a wrong instance connection name; outbound firewall must allow port 3307; `--private-ip` flag for private IP; GKE: "we recommend running the Cloud SQL Auth Proxy in a `sidecar` pattern." — [Cloud SQL Auth Proxy](https://docs.cloud.google.com/sql/docs/mysql/connect-auth-proxy)
- Community reports of proxy errors "Error 403: boss::NOT_AUTHORIZED" and "Possibly missing permission cloudsql.instances.get"; fix is Cloud SQL Client or the two permissions `cloudsql.instances.connect` + `cloudsql.instances.get`. — [Google Developer forum: boss::NOT_AUTHORIZED](https://discuss.google.dev/t/cloud-sql-proxy-error-403-boss/153817); [forum: missing cloudsql.instances.get](https://discuss.google.dev/t/mysql-connection-failure-possibly-missing-permission-cloudsql-instances-get/140910)
- GKE: "The Cloud SQL Auth Proxy is the recommended way to connect to Cloud SQL, even when using private IP"; Workload Identity (KSA bound to GSA) preferred; GSA needs Cloud SQL Client on the instance's project (`roles/cloudsql.instanceUser` for IAM DB auth); "If connecting using private IP, you must use a VPC-native GKE cluster, in the same VPC as your Cloud SQL instance"; Admin API required. — [Connect from GKE](https://docs.cloud.google.com/sql/docs/mysql/connect-kubernetes-engine)
- VPC connection timeout errors from Cloud Run: "dial tcp REMOTE_HOST:REMOTE_PORT: i/o timeout" and "Error: 4 DEADLINE_EXCEEDED: Deadline exceeded" - allow ingress from the connector or Direct VPC subnet in firewall rules and verify routes. — [Cloud Run troubleshooting](https://docs.cloud.google.com/run/docs/troubleshooting)

### Inferences
- Simulator rules: 
  - `Cloud Run -> Cloud SQL (public IP)`: need `cloudsql.client` on runtime SA + Admin API; no VPC needed. Missing role -> 403 notAuthorized / "Possibly missing permission cloudsql.instances.get"; missing API -> "Error 403: Access Not Configured".
  - `Cloud Run -> Cloud SQL (private IP only)`: need Direct VPC egress or connector into the instance's VPC (same region as the service for Direct VPC subnet/connector); missing -> i/o timeout / no route (connection hangs).
  - `VM -> Cloud SQL (private IP)`: VM in same VPC (PSA) or PSC endpoint; peered VPCs don't inherit PSA access transitively (PSA allows "one VPC network").
  - `VM -> Cloud SQL (public IP, direct TCP)`: VM external IP must be in authorized networks; otherwise connection refused/timeout. A VM without an external IP needs Cloud NAT to reach a public IP (inference from PGA/Cloud NAT behavior; not confirmed).
  - `GKE -> Cloud SQL`: proxy sidecar + Workload Identity GSA with `cloudsql.client`; private IP needs VPC-native cluster in same VPC.

## Q7. Compute -> Memorystore Redis; compute -> Google APIs (Firestore, BigQuery, Cloud Storage, Pub/Sub, Secret Manager); Private Google Access

### Takeaway
Memorystore for Redis is reachable only on an internal IP inside its authorized VPC, so serverless callers need Direct VPC egress (recommended) or a connector on that network. Calls to Google APIs need no VPC setup for serverless, but the runtime service account must hold the data-plane role on the destination; VMs with only internal IPs additionally need Private Google Access on their subnet (or another egress path).

### Cited Findings
- Memorystore: "Regardless of the connection mode, Memorystore for Redis always uses internal IP addresses to provision Redis instances"; modes `DIRECT_PEERING` (default, peering not shared with other services) and `PRIVATE_SERVICE_ACCESS` (needed for Shared VPC; "clients from PUPI ranges cannot connect"); default routes can't be imported into the Memorystore VPC. — [Memorystore Redis networking](https://docs.cloud.google.com/memorystore/docs/redis/networking)
- Cloud Run -> Redis: "We recommend that you use Direct VPC egress"; Serverless VPC Access also works; the service "must have access to the Redis instance's authorized VPC network" (read `authorizedNetwork` via `gcloud redis instances describe`, pass to `--network`); deploy `--region` is "the region where your Redis instance is located"; subnet "/26 or larger". — [Connect Redis from Cloud Run](https://docs.cloud.google.com/memorystore/docs/redis/connect-redis-instance-cloud-run)
- Firestore roles: `roles/datastore.user` "Read/write access to data in a Firestore database. Intended for application developers and service accounts"; `roles/datastore.viewer` read; `roles/datastore.owner` full; server client libraries use IAM, mobile/web clients use Security Rules. — [Firestore IAM](https://docs.cloud.google.com/firestore/native/docs/security/iam)
- BigQuery: `roles/bigquery.jobUser` "Provides permissions to run jobs, including queries, within the project" (grantable only on project/folder/org); `roles/bigquery.dataEditor` on a dataset allows creating/updating tables and reading/updating data but "does not include `bigquery.jobs.create`"; `roles/bigquery.dataViewer` read. — [BigQuery access control](https://docs.cloud.google.com/bigquery/docs/access-control)
- Common error when jobUser missing: "Access Denied: Project ...: User does not have bigquery.jobs.create permission in project ..." (forum threads; fix `roles/bigquery.jobUser` at project level). — [Google Developer forum](https://discuss.google.dev/t/access-denied-project-user-does-not-have-bigquery-jobs-create-permission-in-project-error/112756)
- Cloud Storage: error "does not have `storage.objects.create` access to the Google Cloud Storage object" (Cloud Run source deploys) — [Cloud Run troubleshooting](https://docs.cloud.google.com/run/docs/troubleshooting); community fix: grant Storage Object Creator on the bucket; "(or it may not exist)" suffix can also mean wrong bucket name — [Looker community](https://community.looker.com/gc/AI-ML/Service-account-not-having-storage-account-create-access/td-p/513839/jump-to/first-unread-message); [Railway](https://station.railway.com/questions/even-though-i-granted-gcs-permissions-t-34c242ca)

The request failed because the instance could not start successfully." is often a missing Secret Manager permission - grant `roles/secretmanager.secretAccessor` to the service account. — [Cloud Run troubleshooting](https://docs.cloud.google.com/run/docs/troubleshooting)
- Pub/Sub publish: `roles/pubsub.publisher` is the role used for publishing principals (e.g. sinks, notification agents). — [Logging sinks](https://docs.cloud.google.com/logging/docs/export/configure_export_v2); [Monitoring notification options](https://docs.cloud.google.com/monitoring/support/notification-options)
- Private Google Access: "VM instances that only have internal IP addresses (no external IP addresses) can use Private Google Access"; enabled "on a subnet by subnet basis"; if disabled, such VMs "can no longer reach Google APIs and services"; "Private Google Access has no effect on instances that have external IP addresses"; doesn't support `rep.googleapis.com` regional endpoints. — [Private Google Access](https://docs.cloud.google.com/vpc/docs/private-google-access)

### Inferences
- Simulator rules: `Cloud Run -> Memorystore`: require VPC egress on Redis `authorizedNetwork` (same region subnet for Direct VPC); missing -> connection timeout (i/o timeout). `VM -> Memorystore`: VM must be on the authorized network; a VM in a different (even peered) VPC fails with direct peering because peering is not transitive (inference).

## Q8. Cloud Build -> Artifact Registry -> Cloud Run / GKE; image pulls (same and cross project); default service accounts and actAs

### Takeaway
Since May-June 2024, new projects' Cloud Build uses the Compute Engine default SA, which no longer gets Editor automatically, so deploys need explicit roles: `roles/run.admin` (or `roles/run.builder`/developer), `roles/iam.serviceAccountUser` on the runtime SA, and `roles/artifactregistry.writer`. ## Q10. VPC egress for serverless, VM-to-VM firewall basics, deprecations and naming (2026)

### Takeaway
Direct VPC egress is the recommended way for Cloud Run to reach private IPs; Serverless VPC Access connectors are still GA (not deprecated) but cost more and perform worse. - No deprecation announcement for Serverless VPC Access was found; App Engine release notes (June 3, 2026) announce Direct VPC egress in Preview as "a simpler, more cost-effective alternative to Serverless VPC Access connectors"; connectors incur charges even without traffic. — [App Engine Java release notes](https://docs.cloud.google.com/appengine/docs/standard/java/release-notes); [Migrate Shared VPC connector to Direct VPC egress](https://docs.cloud.google.com/appengine/docs/standard/migrate-shared-vpc-direct-vpc)
- App Engine egress: "By default, only requests to private IP addresses are routed through a Serverless VPC connector." — [App Engine application security](https://docs.cloud.google.com/appengine/docs/standard/application-security)
- Rename: Cloud Functions -> Cloud Run functions (Aug 21, 2024); 1st gen now "Cloud Run functions (1st gen)"; 2nd gen functions automatically became Cloud Run functions; 1st/2nd gen docs split. — [Cloud Run functions release notes](https://docs.cloud.google.com/functions/docs/release-notes); [Google Cloud blog](https://cloud.google.com/blog/products/serverless/google-cloud-functions-is-now-cloud-run-functions); [Upgrade 1st gen functions](https://docs.cloud.google.com/functions/1stgendocs/migrating/upgrade-gen1-functions)

Common INVALID connections (each is the absence of any mechanism, or a documented restriction):
1. Cloud Storage -> Cloud SQL (direct): Cloud Storage only emits Pub/Sub notifications / Eventarc events; nothing writes into Cloud SQL without compute (a Cloud Run/function handler or a Cloud SQL import operation run by an admin).
2. Pub/Sub -> Cloud SQL / Firestore / Memorystore (direct): no such subscription type (only pull, push, BigQuery, Cloud Storage).
3. Pub/Sub push -> private IP endpoint (VM internal IP, Memorystore, internal LB): push requires a publicly addressable endpoint.
4. Load balancer -> Cloud SQL / Memorystore / BigQuery: serverless NEGs only support Cloud Run, functions, App Engine, API Gateway; backend buckets only Cloud Storage.
5. Network LB (proxy or passthrough) -> serverless NEG: not supported.
6. Serverless NEG -> service in a different region; serverless NEG with health check; serverless NEG mixed with other NEG types in one backend service.
7. Regional external ALB -> backend bucket; IAP on a backend bucket; IAP + Cloud CDN on the same backend service; IAP on both LB and the Cloud Run service.
8. Multi-region load balancing to App Engine.
9. Eventarc Cloud Storage trigger whose location differs from the bucket's region / multi-region, or bucket in another project.
10. Direct VPC egress subnet in a different region than the Cloud Run service; connector in a different project/region (unless Shared VPC); legacy networks.
11. Scheduler/Tasks token identity from another project; using the Cloud Scheduler service agent as the token identity.
12. Scheduler/Tasks/Workflows/Pub/Sub/Eventarc -> internal-ingress Cloud Run via a custom domain (only `run.app` counts as internal), or from a different project outside the perimeter.
13. HTTP caller -> Cloud Run job (jobs don't serve HTTP; use the Admin API connector to run jobs).
14. OIDC token with a custom domain as `aud`; OAuth access token sent to a Cloud Run `run.app` URL (401).
15. Cloud Storage subscription to a Requester Pays bucket or non-existent bucket.
16. Logging sink to a Pub/Sub regional endpoint or an in-transit-restricted topic.
17. Memorystore via PSA from PUPI client ranges; Memorystore from a VPC other than its authorized network.
18. Browser -> private Cloud Run directly (no ID token).
